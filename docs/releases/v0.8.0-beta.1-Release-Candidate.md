# Executive Summary

This is SchemaCraft AI's first formal Release Candidate, packaging everything that has shipped since the last documented release (v0.7.1) through Sprint 6, Sprint 7, and a live private-beta release-readiness pass performed today. The application code has been feature-complete for a private beta since Sprint 7 closed; what this RC adds on top is verification that actually matters: a live pass against a real (non-production) Supabase database and a real browser found and fixed one genuine launch blocker (a missing database migration that would have broken every authenticated generation) and two real, previously-undetected UI bugs (a severe dark-mode contrast failure, an incorrect page title). Everything in this document has been checked against the repository directly — nothing here is assumed from prior planning documents without re-verification.

**The one thing this RC cannot resolve itself:** the database fix that was verified in dev/staging still needs to run against production, and several environment/dashboard settings need human confirmation. Those are listed explicitly below as Operational Tasks — this is not code work, and this environment has no production credentials to do it.

# Major Fixes Since Sprint 6

These are the fixes specific to this RC-preparation pass, found via live verification rather than static review:

1. **Database migration gap (P0/Critical).** `user_preferences` had no table-creation path anywhere — not a Drizzle migration, not inline SQL — so applying `supabase/rls.sql` for the first time against a real database failed before ever reaching `check_authenticated_rate_limit()` or `delete_own_account()`. Since the rate limiter fails closed on any RPC error, this would have made every authenticated generation request fail from a beta's first user onward. Fixed by generating the missing Drizzle migration (covering `user_preferences` and `generation_rate_limit_events`) and re-applying `rls.sql`; both functions are now confirmed present and callable in the dev/staging database.
2. **Severe dark-mode contrast failure (P1).** `outline`/`ghost`-variant buttons (e.g. "Sign out," "Back to Dashboard") rendered light-mode text color even in a genuinely active dark-mode session — a measured 1.12:1 contrast ratio, effectively invisible text. Fixed by giving both variants an explicit rest-state text color instead of relying on inheritance that wasn't resolving correctly in practice.
3. **Incorrect page title (P1).** Account Settings (`/dashboard/settings`) showed "Project Settings" in the top bar/breadcrumb, because the per-project route-title table matched by URL suffix alone and `/dashboard/settings` happens to share the `/settings` suffix with the per-project settings route. Fixed by requiring an actual `/dashboard/projects/[id]/` path match before that suffix table applies.

All three are described in full technical detail in `CHANGELOG.md`'s "Unreleased" entry and were each independently validated (lint/typecheck/test/build) and committed atomically.

# Known Limitations

- **Production database has not been migrated.** The fix verified in dev/staging (§ "Major Fixes") has not been applied to production — see Operational Tasks.
- **Mobile viewport testing was blocked by a tool limitation**, not performed or waived: the browser-automation environment used for this pass could not actually resize the rendered viewport (`resize_window` reported success but `window.innerWidth` never changed). Substituted with a static code review (no fixed large pixel widths or oversized `min-width` utilities found in primary screens) — this is not equivalent to a real-device confirmation.
- **`--text-muted` text sits around 4.0–4.1:1 contrast** in both light and dark themes (just under the 4.5:1 AA threshold for normal text) — a consistent, non-regressed design choice affecting secondary/tertiary text (timestamps, tab labels, code line numbers), not the severe primary-button failure that was fixed. Disclosed, not fixed, in this pass.
- **Only Gemini serves real traffic.** Anthropic and OpenAI are fully implemented and registered but not provisioned with API keys anywhere, and there's no UI to select a non-default provider.
- **CI has no automatic trigger; the CD workflow is non-functional** (TD-024/AD-006, DevOps-owned, unchanged by this RC).
- **Two Workbench keyboard shortcuts** from the spec's own table were never implemented (TD-023) — low severity, reachable via mouse/command palette.
- **Workbench Fullscreen Mode** hides chrome instantly rather than with an animated transition (TD-021) — a deliberate, documented deferral pending a small product decision.

# Operational Tasks Before Release

None of these are code tasks — the code is done and committed. All require access this environment does not have.

1. **Run the database migration against production.** `npm run db:apply-sql` (or `npm run db:setup`, which also runs `drizzle-kit migrate` first) against the real production `DATABASE_URL`. Idempotent and already verified safe in dev/staging; still have a human review the diff against what's presumably already live in production before running it.
2. **Confirm every environment variable in `.env.example` is set correctly in Vercel's Production environment** (not just Preview) — `NEXT_PUBLIC_SITE_URL` is the single most likely one to be silently wrong (password-reset emails would link to `localhost` for real users if unset).
3. **Confirm Supabase Auth's dashboard-level Site URL / Redirect URLs allowlist includes the production domain** — required for password-reset and signup-confirmation links to resolve correctly; cannot be checked from this repository.
4. **Confirm `GEMINI_API_KEY` has quota headroom for expected beta volume** (60 generations/user/hour × up to 100 users is a real number to plan against).
5. **Make sure whoever is on call during the beta window knows CI/CD does not currently auto-verify or auto-deploy** (Known Limitations, above).

# Rollback Checklist

- **Application code:** standard Vercel rollback to the previous deployment — no database migration in this RC is destructive or one-way at the application layer, so a code rollback alone is safe.
- **Database migration:** `check_authenticated_rate_limit()`, `delete_own_account()`, `user_preferences`, and `generation_rate_limit_events` are all additive (new function/table, nothing altered or dropped from what previously existed). Rolling back the *application code* without rolling back the migration is safe — the new functions simply go unused. Rolling back the migration itself is not expected to be necessary, but if it is: `drop table if exists user_preferences, generation_rate_limit_events cascade;` plus dropping the two functions would fully reverse it (not scripted here — a deliberate manual step, matching this project's "prepare but don't blindly apply" discipline for anything schema-adjacent).
- **No feature flag exists for any Sprint 6/7 feature** — rollback is whole-deployment, not per-feature. Disclosed as a limitation, not fixed in this RC (would be new scope).

- [ ] Sign up → confirmation email arrives and its link resolves to the production domain → first login lands on Dashboard
- [ ] Onboarding card appears for a new user; dismisses permanently after the first successful generation
- [ ] Create a project, generate a schema, all 5 output tabs render in the Workbench
- [ ] Edit & Regenerate from History carries the correct prompt *and* the correct project
- [ ] Export all (zip download) produces a valid archive
- [ ] Deliberately hit the authenticated rate limit; confirm a clear rejection with a retry-time estimate
- [ ] Delete a test account; confirm sign-out and that the account/projects/generations are actually gone
- [ ] Force an error and confirm the branded `ErrorState` recovery UI, not a raw stack trace
- [ ] Visit a nonexistent route; confirm the branded 404

# Beta Success Criteria

- No user is blocked from generating a schema due to a broken rate-limit check (the exact failure mode this RC's P0 fix closes)
- Fewer than 1% of beta sessions encounter an unhandled application error (measurable once basic error tracking/logging exists in production — not yet wired up, itself a candidate for Sprint 8)
- At least a majority of invited users complete one full generation → save → revisit cycle within their first session
- No security-relevant defect (especially around `delete_own_account()`'s `auth.uid()` scoping) surfaces during the beta window

---

# Recommended Initial Beta Size

**10–20 users for the first 48–72 hours**, then scale toward the full 100 if no P0/P1 issue surfaces. Reasoning: this RC's own testing found a P0 (would have blocked 100% of users) and two real P1s that no amount of static review or automated testing caught — a staged rollout gives room to catch anything a live pass with a handful of real, unpredictable users surfaces that this session's own live pass (one account, one browser) could not.

---

# Known Risks

1. **Highest:** the production database migration is the one action standing between this RC and a fully broken authenticated generation path for every real user — entirely operational, not addressed by anything in this RC's own commits.
2. **Second:** a misconfigured `NEXT_PUBLIC_SITE_URL` or Supabase redirect allowlist would silently break password reset/confirmation for real users with no workaround.
3. **Operational:** no automatic CI/CD means any beta-window fix depends on someone remembering to validate and deploy manually and correctly, every time.
4. **Lower:** unverified mobile experience (tool-blocked, not confirmed either way), the disclosed `--text-muted` contrast gap, TD-021/TD-023 Workbench polish items — none of these are "will the product work" risks.

---

# Go / No-Go Recommendation

**Conditional GO.** The application itself has cleared every gate available in this environment: full validation green, a real live pass against a real database and browser, and every issue that pass found has already been fixed and re-verified. The remaining conditions are entirely operational (production migration, environment/dashboard confirmation) and explicitly outside what this execution role can perform. **Recommendation: promote this Release Candidate once, and only once, the five Operational Tasks above are complete and the Smoke-Test Checklist has been run against real production** — at that point this is a genuine GO for an initial 10–20-user beta wave.
